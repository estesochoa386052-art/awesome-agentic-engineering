What is harness engineering?

Harness engineering is the practice of building the constraints, tools, documentation, and feedback loops that make AI coding agents actually work in production. The term was popularized by OpenAI's February 2026 post, but the concept exists across every major engineering organization deploying agents at scale.

The key insight: the bottleneck is never the model. A GPT-4-class model with a well-engineered harness consistently outperforms a frontier model thrown at a raw codebase. Stripe put it bluntly: “The real magic is the infrastructure. The AI agent itself is almost a commodity.”

A harness encompasses: context engineering (what the agent knows), architectural constraints (what the agent can and cannot do), execution environments (isolated devboxes, VMs), feedback loops (linting, CI, review), and tooling (curated MCP servers, APIs, file access).

Core patterns

These patterns have converged independently across every major engineering organization deploying agents at scale. They represent robust solutions, not company-specific quirks.

01
Deterministic–Agentic Hybrid
Alternate fixed logic nodes (linting, CI, git) with LLM nodes (generation, interpretation). The model does not run the system — the system runs the model.
Seen in: Stripe Blueprints, Uber Validator, Meta Confucius
02
Isolated Execution Environments
Agents run in sandboxes identical to human developer machines — devboxes, VMs, containers. Isolation is the permission system. No complex auth needed.
Seen in: Stripe devboxes, Google Cloud VMs (Jules), Anthropic local exec
03
Context Engineering (not prompt engineering)
Curated, structured, contextually relevant information delivered per task. AGENTS.md files, directory-scoped rules, semantic indexes. Over-contextualization is as harmful as under-.
Seen in: OpenAI AGENTS.md, Stripe Toolshed, Uber MCP Gateway
04
Tiered Review Gates
Risk-classified review: documentation gets AI-only review; billing logic, security, and data migrations demand full human scrutiny. Cap CI retries at 2–3 rounds.
Seen in: OpenAI (10-level tiers), Stripe (2 CI rounds max), Amazon (senior sign-off)
05
Background / Async Agent Workflows
The biggest productivity gains come from fire-and-forget background agents, not interactive copilots. Engineers launch 10–20 parallel tasks and review output, not generate it.
Seen in: Stripe Minions, Uber background agents, OpenAI parallel Codex threads
06
Failure as Infrastructure Signal
When an agent struggles, the fix is never “try harder.” Identify what capability or constraint is missing and feed it back into the repository as permanent infrastructure.
Seen in: OpenAI's core principle, Stripe's rule files, Anthropic's two-agent architecture

How to contribute

Add a resource,
open a PR.

This list is maintained by the community. If you've found an engineering blog, paper, framework, or case study that belongs here, contributions are welcome. The bar is: published by an engineering org (not a vendor), describes a real production deployment, and includes at least one concrete metric or architectural detail.

01

Fork the repo

Clone and create a branch named add/your-resource-name

02

Add to README.md

Follow the format below. Include company, year, category tag, and a one-line description with at least one metric.

03

Open a pull request

Use the PR template. A maintainer will review within 48 hours. Automated link-checking runs on every PR.

04

Or use GitHub Issues

Can't write a PR? Open an issue with the resource-submission label and paste the link + description.
